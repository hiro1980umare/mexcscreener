# V2b 事前登録（承認済み: D1・D2・D3）

> **V2の事前登録基準は変更しない。V2bはV2結果を見た後に設計された2回目のdev試行なので、偶然の合格を防ぐため、V2bのc2だけ97.5%区間という、より厳しい基準を追加する。**
> 95%→97.5%への変更は基準を緩めるものではなく、V2bに対する追加の厳格化である。

## 0. 守る条件
1. 2011〜2016年の最終検証期間は完全封印のまま(devのデータは2016-06以降だけ。最終用の株価は凍結後にしか取得できない)。
2. V2bは最大1版。**V2cは作らない**(登録後は、V2とV2bの2つ以外のdev実行をコードが拒否する)。
3. V2bの結果を見てルールを変更しない。登録後にrules_v2b.yamlが1文字でも変わると、dev実行も最終検証も拒否される。
4. 変更内容は実行前に文書化して固定する(この文書 + rules_v2b.yaml + criteria_v2b.yaml をコミット、ハッシュをmanifestに記録)。
5. 閾値の微調整は禁止。V2bには調整できる数値が『3分割』しかない。
6. 最終検証に使うのはV2またはV2bのどちらか1つだけ。最大1回(ロック)。
7. 選択基準は §4 のとおり、V2b実行前に固定。

## 1. 変更するのは1点だけ: Qualityの定義
Timing(v1)・Gate・A/B/C/Dの判定表・6つの成功基準・二段階評価(Tier1/Tier2)は一切変えない。
(rules_v2.yaml と rules_v2b.yaml の差は、quality・version・SECデータの保存先・出所の記録の4か所だけ。テストで検査する。)

**V2のQualityの設計上の弱点**(結果の数字ではなく定義そのものについて): 売上成長率が20点分入っている / 利益率・FCF率が資本で割られておらず業種の違いを測りやすい /
『利益が現金を伴っているか』を直接測っていない / 絶対値の点数でHIGHの割合が年で14〜29%に変動し、しきい値も根拠が弱い。

**V2b: 確立された3指標の、同日・銘柄間の順位の平均**
| 要素 | 定義 | 向き | 先行研究 |
|---|---|---|---|
| 収益性 | 営業利益 ÷ 総資産(最新10-Kの期末) | 高いほど良い | Novy-Marx (2013), Fama-French (2015) |
| 利益の質 | (純利益 − 営業CF) ÷ 総資産 | 低いほど良い | Sloan (1996) |
| 希薄化 | 発行済株式数の1年変化率(分割は調整) | 低いほど良い | Pontiff & Woodgate (2008) |

- 基準日ごとに、Gate通過かつ3要素が揃う銘柄の中で各要素を順位(0〜1)にして等金額平均 → 上位1/3=HIGH、下位1/3=LOW、真ん中=MID。
- 3要素のどれかが取れない銘柄、またはその日の判定可能銘柄が100未満なら判定不能(推定しない)。判定不能は最高でもC。
- 先読み防止はV2と同じ(提出日が基準日より**前**のものだけ)。

**事前に妥当と考えられる理由**: ①3指標はこのバックテストより前に発表された、再現されているファクターで、過去データで選んだものではない。②順位方式は業種・景気による水準の違いを吸収し、調整する数値が増えない。
③『良い会社』を『利益がキャッシュを伴い、資本効率が良く、希薄化しない会社』と定義し直す。

## 2. 正直な限界
- V2の結果(Quality低×Timing高 5.1% ≒ Quality高×Timing高 5.3%)を見た後の設計なので、**dev期間でのV2bの成績は楽観的になる(独立した検証ではない)**。本当の検証は最終期間だけ。
- 3つの効果は発表後に弱まったと報告されている。3か月の効果は小さく(0.3〜1%程度)、この検証の検出力(約±1.2%)では見えない可能性が高い。『効かない』ではなく『示せなかった』となりうる。

## 3. 「RSIにQualityを追加する意味」
- Tier2(V2b_A が RSI単独に勝つか)は、V2と同じく、Tier1を満たした場合にだけ評価する。
- 事前登録する記述的な副次分析(選択基準には使わない): RSI<30 の中での Quality HIGH と LOW の差 / Timing高の中での Quality HIGH と LOW の差(いずれも同日内、各側3件以上の日だけ)。

## 4. 最終検証に進む条件(V2b実行前に固定)
V2は devでTier1を満たさなかったので、最終検証の候補になれない。**V2bが次の(a)(b)(c)をすべて満たした場合にだけ**、V2bで最終検証を最大1回行う。満たさなければ最終検証は行わず、封印のまま『優位性を示せなかった』と報告する。
- (a) V2b_A vs ALL_GATE が dev で c1・c3・c4・c5 を満たす(V2と同じ数値)
- (b) Qualityの上乗せ: V2b_A − T_HIGH_ONLY(同日内の差、3か月後、V2b_Aが10件以上ある日)の平均が 0 超
- (c) c2が **97.5%区間**の下限が0超(かつ採用日数40日以上)
条件を満たしても、最終検証でも同じ符号(c6)でなければ成功と主張しない。コードは凍結時と実行時の両方で、この条件を機械的に検査する。

## 5. 事前に固定する運用
- dev期間で試したルールの版数は、V2とV2bの2つまで。結果を報告するときは、この版数を必ず併記する。
- V2bの結果を見て追加の変更をしたくなっても、変更はしない(V2cは作れない)。
